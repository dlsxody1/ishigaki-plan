**포지션**: **AI 풀스택 개발** (프론트 React/Next.js + 백엔드 ASP.NET Core)

> [!important] 결론부터 — 이 공고는 나에게 상당히 유리하다
> **연차 요건이 `2년 이상 ~ 5년 이하`** 다. 내 경력 2년 3개월이 **하한이 아니라 타겟 구간 안**에 있다. (HIT 공고가 "3년 이상"을 요구해서 갭이 컸던 것과 정반대)

> **진짜 승부처는 하나뿐: C#/.NET 백엔드 갭을 어떻게 다루느냐.**

## 📋 채용공고 원문 정리 (AI 풀스택 개발)

### 주요업무

**프론트엔드 웹 개발 / React (Next.js)**
- 프로젝트 및 기능 요구사항에 따른 화면 구성 및 컴포넌트, 로직 구현
- **AI Agent 등의 채팅 중심 화면 요소와 업무 중심 화면 요소간 연계**
- 백엔드 API 연동 및 **실시간 UI 업데이트** 구현

**백엔드 웹 개발 / ASP.NET Core**
- MVC 기반 컨트롤러, 서비스(DI) 로직의 프론트엔드 연동을 위한 활용, 수정, 추가 개발
- **EF Core**를 활용한 쿼리 구현

**보조 업무 (일부 참여 및 지원)**
- AI Agent 워크플로우, **프롬프트 개발 및 테스트**
- 고객사 및 외부 시스템, API 분석 및 데이터 연동 설계, 구현

**공통사항**
- **Claude Code 등을 활용한 AI 중심 개발 워크플로우 적용** ← 🔥 내 핵심 카드
- 본사 근무 또는 프로젝트 상황에 따른 **고객사 출장, (반)상주 근무**

## 🔍 회사가 뭘 하는 곳인가

한 문장으로: **"기업이 가진 내부 데이터 위에서 일하는 AI 에이전트를, 기업 환경에 맞게 만들어주고 여러 개를 한 곳에서 관리하게 해주는 플랫폼."**

### 제품 라인업 (CXP = Conversational AI eXperience Platform)

| 제품 | 하는 일 | 공고의 어느 업무와 연결되는가 |
| --- | --- | --- |
| **CXP Agent** | 사내 데이터를 이해해 질의응답·정책 검토·보고서 작성 수행 | "**채팅 중심 화면 요소**", 스트리밍 응답, 출처 표시 |
| **CXP Workflow** | 자연어로 워크플로우를 구성하면 에이전트가 end-to-end 처리 | "**AI Agent 워크플로우, 프롬프트 개발 및 테스트**" |
| **CXP Hub** | 수십 개 에이전트를 중앙 통합 관리하는 오케스트레이션 허브 | "**업무 중심 화면 요소**", 관리자 대시보드 |
| 검색 최적화 엔진 / Developer Kit | RAG 검색 품질, 외부 개발자용 SDK | Vector DB, "외부 시스템·API 분석 및 데이터 연동" |
| Azure 클라우드 서비스 | Azure 구축·기술지원 (Microsoft 파트너) | .NET·MAF·Azure 중심 스택인 이유가 여기 있음 |

> [!note] 스택이 왜 하필 C#/.NET인가 — 면접에서 아는 척할 수 있는 포인트
> 랭코드는 **Microsoft 파트너**이고 Azure 클라우드 서비스를 함께 제공한다. 그래서 백엔드가 ASP.NET Core, Agent 프레임워크가 **MAF(Microsoft Agent Framework)** 다. 국내 대기업·금융 고객사 상당수가 **MSSQL + .NET 기반 레거시**를 쓴다는 점과도 맞아떨어진다.
> → "왜 .NET을 쓰는지 이해하고 왔다"는 인상을 주면, C# 경험이 없다는 갭을 상당 부분 상쇄할 수 있다.

> [!important] 기술적 차별점 — "Moderator"
> 대표 인터뷰의 핵심: **비표준 시스템 간 연동**.
> "AI 에이전트끼리 소통하려면 표준 프로토콜이 필요한데, 기존 기업 시스템 상당수는 표준을 따르지 않는다. 랭코드는 이 **비표준 환경**을 처리해 **벤더 락인 리스크를 줄인다.**"
> → 공고의 **"고객사 및 외부 시스템, API 분석 및 데이터 연동 설계, 구현"** 과 **"고객사 현장의 기술 문제를 직접 해결"** 이 바로 이 이야기다. 즉 이 회사에서 개발자의 일은 **깨끗한 신규 개발이 아니라 남의 시스템에 붙이는 일**이라는 걸 알고 가야 한다.

## 💡 회사가 추구하는 가치

1. **"복잡한 업무를 단순하게, 반복 작업을 자동으로"** — 홈페이지 메인 카피.
2. **사람이 방향을 정하고, AI가 의사결정을 리드한다** — 대표가 밝힌 최종 목표. 자동화가 아니라 **인간-AI 협업**.
3. **개방성 / 벤더 중립** — 타사 AI까지 연결하는 통합 허브. 고객의 선택권을 지키는 쪽.
4. **엔터프라이즈 신뢰성** — "데모가 되는 것"과 "대기업 현업에서 돌아가는 것"의 차이를 아는 회사. 공고의 **"프로덕션 수준으로 적용"** 이라는 표현과 같은 맥락.

> [!tip] 이 가치들과 내 이력서가 만나는 한 문장
> **"AI가 만든 결과물을 신뢰할 수 있는 상태로 관리하는 일"** — 제가 개발 프로세스에서 해온 것이고, 랭코드는 그 문제를 **제품 차원에서** 풀고 있는 회사입니다.

## 🧪 면접 전 개념 정리 — RAG · Vector DB

> [!warning] 왜 이걸 준비해야 하나
> 개발 환경에 **Vector DB**가 있고 제품에 **검색 최적화 엔진**이 있습니다. 즉 CXP Agent의 본질은 **RAG 시스템**입니다. "해본 적 없다"고 답하는 건 괜찮지만, **개념도 모른다**고 답하면 제품 이해도가 없는 지원자가 됩니다. 아래는 실무 경험 없이도 대화가 되는 수준까지의 정리입니다.

### 1. RAG가 왜 필요한가

LLM은 **학습 시점에 본 것만** 알고, 회사 내부 문서는 학습 데이터에 없습니다. 그래서 "우리 회사 휴가 규정 알려줘"라고 물으면 모델은 그럴듯하게 지어냅니다(**환각**).

해결책은 두 가지인데, 실무에서는 대부분 RAG를 씁니다.

| 방식                                       | 설명                                  | 한계                                                 |
| ---------------------------------------- | ----------------------------------- | -------------------------------------------------- |
| **파인튜닝**                                 | 사내 데이터로 모델을 추가 학습                   | 비용·시간 큼, 문서가 바뀔 때마다 재학습, **출처를 못 밝힘**, 권한별 분리가 어려움 |
| **RAG** (Retrieval-Augmented Generation) | 질문할 때마다 **관련 문서를 찾아서 프롬프트에 같이 넣어줌** | 검색이 틀리면 답도 틀림 (그래서 "검색 최적화 엔진"이 제품이 됨)             |

> **한 문장 정의**: "모델을 바꾸는 대신, **질문할 때마다 근거 문서를 찾아 프롬프트에 끼워 넣어** 답하게 하는 방식."

### 2. 전체 파이프라인 (2단계로 나눠서 외우면 안 헷갈림)

**① 인덱싱 단계 (미리 준비 — 문서가 추가/변경될 때)**

```
원본 문서(PDF·워드·위키·DB)
  → 파싱 (텍스트 추출, 표·이미지 처리)
  → 청킹 (Chunking: 적당한 크기로 자르기)
  → 임베딩 (Embedding: 각 청크를 숫자 벡터로 변환)
  → Vector DB에 저장 (벡터 + 원문 + 메타데이터)
```

**② 검색·생성 단계 (사용자가 질문할 때마다)**

```
사용자 질문
  → 질문도 같은 모델로 임베딩 (벡터로 변환)
  → Vector DB에서 유사도 높은 청크 top-k 검색
  → (선택) 리랭킹으로 상위 결과 재정렬
  → 프롬프트에 주입: "다음 문서를 근거로만 답하라: [청크들]" + 질문
  → LLM 응답 생성 + 어떤 문서를 썼는지 출처(citation) 표시
```

### 3. 핵심 용어 (각각 한 줄로 말할 수 있게)

| 용어 | 한 줄 설명 | 면접에서 덧붙일 포인트 |
| --- | --- | --- |
| **임베딩(Embedding)** | 텍스트를 의미를 담은 고차원 숫자 벡터로 바꾸는 것 | 의미가 비슷하면 벡터 공간에서 **가깝게** 위치함 |
| **Vector DB** | 벡터를 저장하고 "가장 가까운 벡터"를 빠르게 찾아주는 DB (pgvector, Pinecone, Qdrant 등) | 전체 비교는 O(n)이라 느림 → **ANN(근사 최근접 탐색, HNSW 등)** 으로 속도를 얻고 정확도를 조금 포기 |
| **유사도(Similarity)** | 보통 **코사인 유사도** — 두 벡터가 이루는 각도로 의미의 가까움 측정 | 크기가 아니라 **방향**을 본다는 게 포인트 |
| **청킹(Chunking)** | 긴 문서를 검색 단위로 자르는 것 | **여기가 품질의 8할.** 너무 크면 노이즈가 섞이고, 너무 작으면 문맥이 잘림. 그래서 **오버랩(겹쳐 자르기)** 을 둠 |
| **top-k** | 유사도 상위 몇 개를 가져올지 | k를 키우면 놓칠 확률↓ 대신 **노이즈↑·토큰 비용↑** |
| **리랭킹(Rerank)** | 1차로 넓게 가져온 뒤, 정교한 모델로 다시 순위 매기기 | "빠른 검색 → 정확한 재정렬" 2단계 전략 |
| **하이브리드 검색** | 키워드 검색(BM25) + 벡터 검색을 섞음 | **고유명사·제품코드·사번**은 의미 검색이 오히려 약함 → 엔터프라이즈에서 특히 중요 |
| **메타데이터 필터링** | 부서·권한·문서종류·기간으로 검색 범위를 먼저 좁힘 | 🔥 **엔터프라이즈의 핵심 — 권한 없는 문서가 검색되면 그대로 정보 유출** |
| **컨텍스트 윈도우** | 프롬프트에 넣을 수 있는 최대 토큰 | 검색 결과를 무한정 못 넣음 → 무엇을 넣고 뺄지가 설계 문제 |
| **그라운딩(Grounding) / 출처** | "찾은 문서 안에서만 답하라"고 제약하고 근거를 표시 | 환각을 줄이는 가장 실용적인 장치. **답을 못 찾으면 모른다고 말하게** 하는 것도 설계 |

### 4. "왜 그냥 키워드 검색이 아니라 Vector DB인가" (자주 묻는 질문)

키워드 검색은 **글자가 겹쳐야** 찾습니다. "연차 며칠 쓸 수 있어?"라고 물었을 때 문서에는 "**휴가 부여 일수**"라고 쓰여 있으면 키워드로는 못 찾습니다.
임베딩은 **의미**를 벡터로 바꾸기 때문에 글자가 달라도 가까운 위치에 놓입니다. 그래서 자연어 질문에 강합니다.
반대로 "**SKU-4821 재고**"처럼 정확한 문자열이 중요한 경우는 키워드 검색이 더 정확합니다. → **그래서 하이브리드로 섞습니다.**

### 5. RAG가 실패하는 지점 (이걸 말하면 "생각해본 사람"으로 보임)

1. **검색이 틀리면 생성도 틀린다** — 대부분의 RAG 실패는 LLM이 아니라 **리트리버(검색)** 의 실패
2. **청킹 경계에서 문맥이 잘림** — 표나 조항이 중간에 잘리면 답이 반쪽이 됨
3. **top-k를 늘리면 노이즈가 섞여 오히려 답이 나빠짐** — 많이 넣는다고 좋아지지 않음
4. **문서가 서로 모순될 때** — 구버전 규정과 신버전 규정이 같이 검색되면 모델이 아무거나 고름 → 최신성 메타데이터·버전 관리 필요
5. **권한 필터링 누락** — 기능이 아니라 **사고**가 됨
6. **평가를 안 함** — "잘 되는 것 같다"로 운영하다 조용히 나빠짐

### 6. 평가는 두 층으로 나눠서 (프롬프트 테스트 질문과도 연결됨)

- **검색 품질**: 정답이 들어있는 문서가 top-k 안에 들어왔는가 (Recall@k, MRR)
- **생성 품질**: 찾아온 문서에 **근거해서** 답했는가(faithfulness), 질문에 실제로 답했는가(relevance)
- 핵심은 **둘을 분리해서 측정**하는 것 — 답이 나쁠 때 검색 탓인지 프롬프트 탓인지 알 수 있어야 고칠 수 있음

### 7. 프론트엔드 개발자로서 RAG에 기여할 수 있는 지점 (이게 내 답변의 착지점)

- **출처(citation) UI** — 어느 문서 몇 페이지를 근거로 답했는지 보여주고 원문으로 이동. 신뢰의 대부분이 여기서 만들어짐
- **"모른다"의 표현** — 검색 결과가 부실할 때 억지 답변 대신 무엇이 부족한지 보여주는 UX
- **스트리밍 응답 렌더링** — 토큰 단위 갱신 시 리렌더 최적화 (→ 입원 차트 경험과 동일한 문제)
- **피드백 루프** — 👍/👎와 "이 답이 왜 틀렸는지"를 수집해 검색 품질 개선 데이터로 연결
- **권한에 따른 화면 제어** — 단, 실제 차단은 서버·검색 단계라는 걸 알고 있을 것

> [!tip] 면접용 30초 스크립트
> "RAG는 모델을 새로 학습시키는 대신, 질문이 들어올 때마다 사내 문서에서 관련 부분을 찾아 프롬프트에 근거로 넣어주는 방식으로 이해하고 있습니다. 문서를 청킹해서 임베딩으로 벡터화해 Vector DB에 넣어두고, 질문도 같은 방식으로 벡터로 바꿔 유사도가 높은 상위 몇 개를 가져와 '이 문서를 근거로 답하라'고 주입하는 구조입니다. 제가 이해하기로 품질을 가르는 건 모델보다 **청킹 전략과 검색 품질**이고, 엔터프라이즈에서는 여기에 **권한 기반 메타데이터 필터링**이 반드시 붙어야 한다고 봅니다. 직접 구축해본 경험은 없지만, 프론트엔드에서는 **출처 표시와 '모른다'를 제대로 보여주는 UX**가 신뢰를 만드는 지점이라고 생각합니다."

> [!note] 예상 꼬리질문
> - **Q. 청크 크기는 어떻게 정하시겠어요?** → 정답은 없고 문서 성격에 따라 다름. 규정·계약서처럼 조항 단위가 뚜렷하면 **구조 기반 분할**, 서술형이면 고정 길이 + 오버랩. **평가 세트를 만들어 실측**해서 정하는 게 원칙
> - **Q. 사용자가 "작년 매출 알려줘"라고 물었는데 엉뚱한 문서를 가져오면 어디부터 보시겠어요?** → 검색 단계부터. 실제로 어떤 청크가 top-k로 왔는지 로그를 먼저 확인 → 검색이 맞았는데 답이 틀렸으면 프롬프트/모델 문제로 분리
> - **Q. 문서가 매일 바뀌면 인덱스는 어떻게 관리하죠?** → 변경분만 재임베딩(증분 인덱싱), 문서 버전·유효기간 메타데이터, 삭제 문서의 인덱스 제거
> - **Q. 사용자마다 볼 수 있는 문서가 다르면?** → 검색 시점에 **사용자 권한을 메타데이터 필터로 적용**. 검색 후 필터링하면 top-k가 다 걸러져 빈 답이 나올 수 있으므로 **검색 전에** 거는 게 맞음
> - **Q. LLM이 문서에 없는 내용을 지어내면 어떻게 막나요?** → 프롬프트로 근거 제한 + 출처 강제 + 근거 없으면 모른다고 답하게 + 응답의 주장이 원문에 있는지 검증하는 후처리

### 📌 발견 1 — Azure 실무 경험이 이미 있다 ⭐ 이력서 수정 필요

`vitalvet-front/.github/workflows/development.yml` — **배포 대상이 AWS가 아니라 Azure다.**

- `azure/login@v2` + **OIDC 페더레이션**(client-id/tenant-id/subscription-id, `id-token: write` 권한)으로 토큰 교환

- `index.html` / `sw.js` / `manifest.webmanifest`는 **캐시 헤더를 따로 지정해 개별 업로드** — "sync는 파일별 캐시 헤더를 못 지정하고, 캐시되면 PWA가 구버전에 갇힌다"는 이유가 주석으로 남아 있음

> [!tip] 이게 왜 중요한가
> 랭코드는 **Microsoft 파트너**이고 우대사항 1번이 **"클라우드 서비스 활용 경험 (Azure, AWS 등)"** 입니다. 앞에서 "Azure 경험 없음"이라고 적었던 건 **틀렸습니다.** Azure Blob 정적 호스팅 + OIDC 인증 + CDN 캐시 전략까지 직접 다뤄본 경험이 있습니다.
> 면접 답변: **"현재 서비스는 GitHub Actions에서 OIDC로 Azure에 로그인해 Blob Storage `$web`에 배포하고 있고, 제가 그 파이프라인을 다뤘습니다. PWA 서비스워커가 구버전에 갇히는 문제 때문에 HTML·sw.js·manifest만 no-cache로 따로 올리도록 나눠뒀습니다."**

> [!important] 실제 경험 — 이대로 말하면 됩니다

>
> **① 같은 컴포넌트를 계속 새로 만들어냄**
> 이미 존재하는 버튼·모달·인풋을 찾아 쓰지 않고, 매번 비슷한 컴포넌트를 새로 생성했습니다. 컨텍스트에 기존 코드가 다 들어오지 않으니 **"없으면 만든다"** 로 동작한 겁니다. 그 결과 거의 같은 컴포넌트가 여러 벌 생기고, 디자인 수정 하나가 여러 파일로 번지는 상태가 됐습니다.

> 비즈니스 로직도, API 호출도, UI도 전부 한 파일 안에 들어가 있었습니다. 동작은 하지만, **FSD로 레이어를 나눠둔 의미가 완전히 사라진 상태**였습니다.
>
> **그래서 어떻게 했나**
> 리뷰에서 매번 잡는 건 한계가 있다고 판단했습니다. 사람이 놓치면 그대로 들어가니까요. 그래서 **FSD 규칙을 위반하면 커밋 자체가 안 되도록 커스텀 린트 훅을 만들었습니다.** 구조 위반 7종을 커밋 전에 자동으로 차단하는 방식입니다.
>
> **여기서 배운 것**
> AI가 코드를 잘못 짜는 게 문제가 아니라, **잘못 짤 수 있다는 전제 위에 개발 환경이 설계돼 있지 않은 게** 문제였다고 생각합니다. 그래서 규칙을 문서가 아니라 **도구가 강제하도록** 옮겼습니다.

#### 🅴 Q. AI 코드 리뷰는 어떻게 하시나요? PR에서 뭘 보시나요?

- AI가 짠 코드에서 특히 자주 보는 것: **불필요한 추상화·중복 구현·과도한 방어 코드·안 쓰는 props·타입 `any` 회피용 캐스팅**

- ✅ **팀에 AI 1차 리뷰 파이프라인이 있음** — 이슈 라벨로 위임된 작업은 Draft PR 전에 AI가 완료 조건과 대조해 1차 리뷰를 하고, 사람이 최종 확인 (⚠️ 파이프라인 자체는 팀 인프라 담당이 구축 — 아래 ⛔ 섹션 참고)

### 3) 프론트엔드 (주력)

### Q1. AI Agent 채팅 화면에서 프론트엔드가 가장 어려운 지점은?

**의도**: 채팅 UI를 "그냥 리스트 렌더링"으로 보는지, 스트리밍이라는 고빈도 상태 변경 문제로 보는지 구분하려는 질문. 실제로 만들어본 사람만 아는 함정이 있는 영역입니다.

**두괄식 답변**

> "세 가지가 어려웠습니다. 첫째는 스트리밍의 리렌더 비용, 둘째는 결과가 불확실한 작업의 UX 상태 설계, 셋째는 대화가 길어질 때의 성능입니다. 특히 첫 번째는 이전에 입원 환자 차트에서 실시간 데이터를 다룰 때와 구조적으로 같은 문제였습니다."

#### ① 스트리밍 — 토큰 단위 상태 갱신

문제부터 정확히 짚는 게 좋습니다.

토큰 하나당 `setState`를 호출하면 초당 30~60회 상태 변경이 발생합니다. 여기서 진짜 비용은 텍스트 노드 업데이트가 아니라, **메시지 배열이 새 참조가 되면서 리스트 전체가 재조정(reconciliation)되는 것**입니다. 대화가 200턴이면 토큰 하나마다 200개 컴포넌트가 diff를 돕니다.

해결은 계층적으로 접근했다고 말하는 게 설득력 있습니다.

**1) 버퍼링 — 토큰 수신과 렌더 주기를 분리**

ts

```ts
function useStreamBuffer(onFlush: (text: string) => void) {
  const bufferRef = useRef('');
  const rafRef = useRef<number | null>(null);

  const push = useCallback((token: string) => {
    bufferRef.current += token;
    if (rafRef.current !== null) return;

    rafRef.current = requestAnimationFrame(() => {
      onFlush(bufferRef.current);
      rafRef.current = null;
    });
  }, [onFlush]);

  return push;
}
```

`throttle(50ms)`보다 `requestAnimationFrame`을 선호한 이유를 덧붙이면 좋습니다. 브라우저 페인트 주기에 정렬되어 낭비되는 렌더가 없고, 탭이 백그라운드면 자동으로 멈춥니다. 다만 rAF는 프레임당 1회라 초당 60회가 될 수 있어서, 실제로는 **rAF + 최소 간격(약 40~80ms)** 를 같이 걸었다고 하면 더 구체적입니다.

**2) 렌더 범위 격리 — 완료된 메시지와 진행 중 메시지 분리**

핵심은 스트리밍 중인 텍스트를 메시지 배열에 넣지 않는 것입니다.

```
messages: Message[]        // 확정된 메시지. 불변, memo 대상
streamingMessage: string   // 진행 중. 별도 슬라이스, 별도 컴포넌트만 구독
```

이렇게 하면 토큰이 아무리 빨리 와도 리렌더 대상은 마지막 말풍선 하나뿐입니다. 스트리밍이 끝나는 순간 `messages`에 push하고 버퍼를 비웁니다. Zustand라면 selector로 구독 범위를 좁히고, 외부 스토어라면 `useSyncExternalStore`로 붙입니다.

**3) 마크다운 파싱 비용 — 자주 놓치는 부분**

이걸 언급하면 차별화됩니다. 토큰마다 전체 마크다운을 재파싱하면 rAF로 렌더를 줄여도 CPU가 그대로 탑니다. 게다가 코드블록이 열리다 만 상태(` ``` `만 온 상태)에서는 파서가 깨진 트리를 만듭니다.

> "스트리밍 중에는 경량 렌더나 plain text로 보여주고, syntax highlighting과 완전한 마크다운 렌더는 스트림 종료 후 한 번만 수행했습니다. 하이라이팅은 Web Worker로 뺐고요."

**4) 자동 스크롤 — 사용자 의도 존중**

무조건 하단 고정을 하면 사용자가 위로 올려 읽는 중에 강제로 끌려 내려옵니다. `scrollTop + clientHeight >= scrollHeight - threshold`로 "하단 근처인지"를 판단해 stick 여부를 결정하고, 사용자가 위로 스크롤하면 해제 + "최신으로" 버튼을 노출합니다. CSS `overflow-anchor`도 같이 언급하면 좋습니다.

#### ② 불확실한 결과를 다루는 UX

여기가 일반 챗봇과 **Agent**의 차이가 드러나는 지점입니다. Agent는 도구를 호출하고, 중간에 실패하고, 오래 걸립니다.

**상태를 boolean으로 관리하면 무너집니다.** `isLoading`, `isError`, `isStreaming` 세 개면 8가지 조합 중 불가능한 상태가 생깁니다. 판별 유니온으로 가야 합니다.

ts

```ts
type AgentTurn =
  | { status: 'idle' }
  | { status: 'submitted' }
  | { status: 'streaming'; text: string }
  | { status: 'tool_running'; text: string; tool: ToolCall }
  | { status: 'aborted'; text: string }        // 중단 시점까지의 부분 응답 보존
  | { status: 'failed'; text: string; error: AgentError; retryable: boolean }
  | { status: 'done'; message: Message };
```

**취소(abort)**: `AbortController`를 fetch에 연결하고, 서버에도 취소를 알려 토큰 과금을 멈춰야 합니다. 여기서 정책 결정이 필요합니다 — 중단 시점까지 받은 부분 응답을 남길 것인가, 버릴 것인가. 저는 남기고 "중단됨" 배지를 붙이는 쪽을 택했다고 하면 사용자 관점을 고려한 걸로 보입니다.

**부분 실패**: 도구 3개를 호출했는데 1개만 실패한 경우, 메시지 전체를 에러로 처리하면 나머지 결과가 버려집니다. **메시지 단위가 아니라 블록 단위로 상태를 갖게** 설계해야 합니다.

**재시도**: 같은 요청을 다시 보내면 이전 응답을 덮어쓸지 버전으로 쌓을지 결정해야 합니다. 사내 업무 도구라면 "이전 답변이 뭐였는지" 추적이 중요하니 버전 히스토리 쪽이 유리합니다.

**출처 표시**: 인용을 텍스트 스트림에 섞어 파싱하면 취약합니다. SSE의 `event:` 타입을 나눠 `citation` 이벤트를 별도로 받아 후처리하는 구조가 안전합니다.

#### ③ 긴 대화 기록 성능

- **가상화의 함정**: 채팅은 높이가 가변인데, 마크다운 안의 이미지·표·코드블록이 로드되면서 높이가 사후에 바뀝니다. `estimateSize`만으로는 스크롤이 튀어서 `measureElement` 기반 동적 측정이 필요합니다. TanStack Virtual을 썼다면 이 지점을 언급하세요.
- **역방향 무한 스크롤**: 위로 올려 과거를 불러올 때 기존 스크롤 위치를 보정하지 않으면 화면이 점프합니다. 로드 전 `scrollHeight`를 기록해 차이만큼 `scrollTop`을 더해주는 처리가 필요합니다.
- **정규화 저장**: 메시지를 `Record<id, Message>` + `id[]`로 관리해 한 건 수정이 배열 전체 교체로 번지지 않게 합니다.

**예상 꼬리질문**

- "rAF 대신 throttle을 쓰면 뭐가 달라지나요?"
- "가상화를 넣었을 때 Ctrl+F 검색이나 접근성은 어떻게 처리했나요?" → 가상화의 실질적 트레이드오프. 검색·복사·스크린리더 순회가 깨진다는 점을 인정하고, 그래서 **대화가 N턴 넘을 때만 가상화를 켜는 방식**을 택했다고 답하면 좋습니다.

### Q2. "채팅 중심 화면과 업무 중심 화면의 연계"란 무엇이라 생각하나요?

**의도**: 이건 십중팔구 그 회사 제품(CXP Agent)의 실제 과제입니다. 채팅을 사이드 위젯 정도로 보는지, **같은 상태를 두 개의 뷰로 보는 문제**로 보는지를 봅니다.

**두괄식 답변**

> "대화로 지시한 결과가 실제 업무 데이터에 반영되고, 반대로 업무 화면의 맥락이 대화에 들어가는 양방향 구조라고 봅니다. 결국 두 화면이 같은 상태를 봐야 한다는 문제라서, 서버 상태 동기화 전략이 핵심이 됩니다."

**구체적인 시나리오를 들어주세요.** 추상적으로 말하면 점수가 안 나옵니다.

> "예를 들어 사용자가 '이번 분기 미결재 건 정리해줘'라고 하면 오른쪽 테이블의 필터와 정렬이 실제로 바뀌어야 하고, 반대로 테이블에서 특정 행을 선택한 채로 '이거 왜 반려됐어?'라고 물으면 그 행이 대화 컨텍스트로 들어가야 합니다."

**설계 관점 세 가지**

**1) 상태 소유권 분리**

서버 상태(결재 목록, 문서)는 TanStack Query가 단일 소유자이고, 채팅 UI 상태(입력값, 스트리밍 버퍼)는 로컬입니다. 채팅이 서버 데이터를 자체 복사본으로 들고 있으면 두 화면이 즉시 어긋납니다.

**2) 무효화 대상을 프론트가 추측하지 않기**

Agent가 어떤 도구를 호출해 무엇을 바꿨는지 프론트가 알 수 없습니다. 여기서 좋은 답변은 **계약을 제안하는 것**입니다.

> "Agent 응답의 종료 이벤트에 서버가 변경된 리소스 목록을 내려주고, 프론트는 그걸 쿼리 키로 매핑해 무효화하는 구조를 제안했습니다. 프론트가 '이 명령이면 아마 결재 목록이 바뀌겠지'라고 추측하면 도구가 추가될 때마다 프론트를 고쳐야 해서 결합도가 폭발합니다."

ts

```ts
// 서버가 내려주는 종료 이벤트
{ type: 'done', affected: [{ resource: 'approvals', scope: { teamId: 'A' } }] }

// 프론트는 매핑만 담당
affected.forEach(({ resource, scope }) =>
  queryClient.invalidateQueries({ queryKey: [resource, scope] })
);
```

**3) 낙관적 업데이트는 선별적으로**

여기서 뉘앙스를 보여주면 좋습니다. 일반 CRUD와 달리 **Agent 작업은 비결정적이고 오래 걸려서 낙관적 업데이트가 대체로 부적합합니다.** 결과를 미리 그려놓고 실패하면 롤백하는 게 사용자에게 더 혼란스럽고, 결재 같은 도메인에선 위험하기까지 합니다.

> "단순하고 결과가 확정적인 작업(즐겨찾기 토글 등)만 낙관적으로 처리하고, Agent가 수행하는 업무 변경은 '처리 중' 상태를 명시적으로 보여준 뒤 서버 확정 후 반영했습니다."

**4) URL을 공유 상태로 활용** (여유 있으면)

채팅 지시로 바뀐 필터를 URL 쿼리에 반영하면 업무 화면이 자연스럽게 반응하고, 그 상태를 동료에게 링크로 공유하거나 새로고침해도 재현됩니다. 두 화면을 직접 연결하는 대신 URL을 매개로 두면 결합도가 낮아집니다.

**예상 꼬리질문**

- "Agent가 잘못된 변경을 했을 때 되돌리기는 어떻게 하시겠어요?"
- "두 화면이 동시에 같은 데이터를 수정하면요?"

### Q3. SSE와 WebSocket 중 무엇을 고르시겠어요?

**의도**: 유행이 아니라 요구사항으로 기술을 고르는지, 그리고 **운영 이슈**를 아는지 봅니다.

**두괄식 답변**

> "Agent 응답 스트리밍처럼 서버→클라이언트 단방향이면 SSE가 적합하다고 봅니다. 기존 HTTP 인프라를 그대로 쓰고 인증·프록시·로깅이 다 재사용되며 재연결이 표준으로 제공됩니다. 협업 편집이나 다중 사용자 프레즌스처럼 양방향 저지연이 필요하면 WebSocket을 씁니다."

**SSE를 택할 때의 실무 디테일** — 이걸 알면 "써봤구나" 소리를 듣습니다.

- **`EventSource` 대신 fetch + ReadableStream**: `EventSource`는 커스텀 헤더를 못 넣어서 `Authorization` 전달이 안 됩니다. 실무에서는 `fetch` + `ReadableStream`으로 직접 파싱하는 경우가 많습니다. 대신 자동 재연결을 직접 구현해야 하는 트레이드오프가 생깁니다.
- **HTTP/1.1 커넥션 제한**: 도메인당 6개 제한 때문에 탭을 여러 개 열면 막힙니다. HTTP/2 이상이면 해소됩니다.
- **프록시 버퍼링**: nginx `proxy_buffering off`를 끄지 않으면 응답이 뭉쳐서 한 번에 옵니다. "로컬에선 되는데 배포하면 스트리밍이 안 되는" 전형적인 원인이라 언급하면 좋습니다.
- **유휴 타임아웃**: LB가 커넥션을 끊지 않도록 주기적으로 keep-alive 코멘트(`:` 라인)를 보냅니다.
- **재개**: `Last-Event-ID`로 끊긴 지점부터 이어받을 수 있지만, 실제로는 서버가 중간 상태를 들고 있어야 해서 "재연결 시 해당 턴을 재조회"로 처리하는 게 현실적입니다.

**WebSocket의 비용**: 인증 토큰 만료 시 갱신이 까다롭고, 재연결·백오프·하트비트를 직접 만들어야 하며, 스케일아웃 시 sticky session이나 pub/sub 브로커가 필요합니다.

**마무리 한 문장**

> "요구사항이 단방향인데 WebSocket을 쓰면 운영 복잡도만 늘어난다고 생각합니다."

### Q4. FSD를 도입한 이유와 실제로 불편했던 점은?

**의도**: 아키텍처를 남이 좋다니까 따라 쓴 건지, 문제를 겪고 선택한 건지. **불편했던 점을 솔직히 말하는 게 핵심**입니다. 장점만 나열하면 감점입니다.

**도입 이유 — 겪은 문제부터**

> "기능이 늘면서 `components` 폴더가 수십 개로 불어났고, 어떤 컴포넌트가 어디서 쓰이는지 파악이 안 돼서 수정할 때마다 전체 검색을 해야 했습니다. FSD는 레이어 간 의존 방향을 단방향으로 강제하기 때문에 순환 참조가 구조적으로 막히고, 기능을 삭제할 때 슬라이스 폴더 하나를 지우면 되는 점이 컸습니다. `eslint-plugin-boundaries`로 규칙을 CI에서 강제했습니다."

**불편했던 점 — 여기가 진짜 답변**

1. **레이어 판단이 애매한 경우가 자주 생김.** `widgets`와 `features` 경계가 특히 모호했습니다. "결재 목록 위젯"이 사용자 행동(승인)을 포함하면 feature인지 widget인지 매번 논쟁이 붙었고, 결론이 사람마다 달랐습니다. 그래서 팀에서 **"결정 로그"를 만들어 판단 사례를 누적**했습니다.
2. **`entities` 과설계.** 도입 초기에 모든 도메인 모델을 entities로 만들었는데, 실제로는 한 feature에서만 쓰이는 게 대부분이라 파일만 늘고 이득이 없었습니다. **두 곳 이상에서 쓰일 때 승격**하는 규칙으로 바꿨습니다.
3. **슬라이스 간 직접 참조 금지 규칙의 우회 유혹.** feature A가 feature B의 컴포넌트를 쓰고 싶을 때 정석은 상위 widget에서 조합하는 것인데, 급하면 그냥 import하고 싶어집니다. 린트로 막아뒀지만 예외 주석이 쌓이는 걸 주기적으로 정리해야 했습니다.
4. **러닝커브.** 새로 합류한 분이 "이 파일을 어디에 둬야 하나"로 하루를 씁니다. 규모가 작은 프로젝트에는 과합니다.

**마무리**

> "그래서 지금은 프로젝트 규모에 따라 레이어를 줄여서 적용합니다. 작은 프로젝트는 `features` + `shared`만으로도 충분하다고 봅니다."

### Q5. App Router의 서버 컴포넌트를 써보셨나요? SSR과 CSR을 어떻게 나누나요?

**의도**: 'use client'를 최상단에 박고 사실상 CSR로 쓰는 사람이 많습니다. **경계 설계**를 아는지 봅니다.

**기준 한 줄**

> "상호작용과 브라우저 API가 필요한 곳만 클라이언트로 내리고, 나머지는 서버에 둡니다. 실무에선 'use client'를 가능한 한 잎(leaf) 쪽으로 밀어내는 게 핵심이었습니다."

**구체적 배분**

|서버 컴포넌트|클라이언트 컴포넌트|
|---|---|
|초기 목록·상세 데이터 페치|채팅 입력·스트리밍 렌더|
|정적 레이아웃, 권한별 메뉴 구성|폼, 드래그앤드롭, 모달|
|마크다운 → HTML 사전 변환|무한 스크롤·가상화|

특히 **무거운 라이브러리를 서버에 두면 클라이언트 번들에서 통째로 빠진다**는 점이 실질적 이득입니다. 마크다운 파서와 하이라이터는 수백 KB라 저장된 대화를 다시 볼 때는 서버에서 렌더해 내려주는 게 유리합니다.

**알면 좋은 패턴 — children으로 서버 컴포넌트 주입**

클라이언트 컴포넌트 안에 서버 컴포넌트를 직접 쓸 수는 없지만, `children`으로 넘기면 됩니다.

tsx

```tsx
// ChatLayout.tsx (client) — 리사이즈 등 상호작용 담당
'use client';
export function ChatLayout({ children, panel }: Props) { ... }

// page.tsx (server)
<ChatLayout panel={<ApprovalTable />}>  {/* ApprovalTable은 서버 컴포넌트 */}
  <ChatStream />
</ChatLayout>
```

**TanStack Query와의 연결**: 서버에서 `prefetchQuery` → `dehydrate` → `HydrationBoundary`로 넘기면 초기 로딩 워터폴 없이 클라이언트 캐시가 채워집니다. 채팅 화면에서 이전 대화 목록을 이렇게 처리했다고 말하면 Q2와 자연스럽게 이어집니다.

**솔직한 트레이드오프 한마디**

> "사내 시스템은 SEO가 필요 없어서 SSR의 이점이 초기 로딩과 번들 크기 쪽에 집중됩니다. 그래서 모든 걸 RSC로 옮기기보다, 무거운 초기 데이터와 큰 라이브러리를 서버로 보내는 선에서 실용적으로 적용했습니다."

주의점을 하나 덧붙이면 좋습니다 — Server Action은 순차 실행되어 병렬 호출이 안 되고, 캐시 무효화(`revalidateTag`)와 TanStack Query 캐시가 **서로 다른 두 개의 캐시 계층**이라 이 둘을 어떻게 정렬할지가 실무의 진짜 고민입니다.

### Q6. 사내 데이터를 다루는데 프론트엔드 보안에서 주의할 점은?

**의도**: "XSS 조심합니다" 수준인지, LLM 제품 특유의 위협을 아는지 봅니다.

**① 마크다운/HTML 렌더링 — 여기서 차별화하세요**

기본은 `dangerouslySetInnerHTML` 전에 DOMPurify로 sanitize, 허용 태그 화이트리스트, `javascript:` 스킴 차단, 외부 링크 `rel="noopener noreferrer"`입니다.

그런데 **AI 응답에는 일반 XSS와 다른 위협이 있습니다.**

> "LLM 출력은 사용자 입력만큼 신뢰할 수 없는 데이터로 취급해야 합니다. 특히 프롬프트 인젝션으로 조작된 응답이 마크다운 이미지를 포함하면, 이미지 URL 쿼리에 사내 데이터를 실어 외부 서버로 유출할 수 있습니다. 브라우저가 자동으로 요청을 보내니까 사용자가 클릭할 필요도 없습니다."

대응은 CSP `img-src`를 신뢰 도메인으로 제한하거나, 외부 이미지를 자동 로드하지 않고 사용자 확인 후 로드하는 방식입니다. 이 답변 하나로 "LLM 제품 경험이 있구나"라는 인상을 줄 수 있습니다.

**② 토큰 저장**

`localStorage`는 XSS 한 번이면 전부 털립니다. `httpOnly` + `Secure` + `SameSite` 쿠키가 기본이고, refresh 토큰 회전을 적용합니다. 다만 SSE를 `EventSource`로 쓸 때 헤더를 못 넣는 문제와 맞물리는데, 쿠키 방식이면 오히려 자동으로 실려서 궁합이 좋다는 점을 연결하면 Q3과 이어집니다.

**③ 테넌트·권한별 노출 제어**

> "프론트에서 메뉴나 버튼을 숨기는 건 UX이지 보안이 아니라는 전제로 작업했습니다. 실제 차단은 서버에서 하고, 프론트는 응답에 없는 데이터를 그리지 않도록 방어적으로 처리했습니다."

Agent 특유의 리스크도 짚으면 좋습니다 — **A 부서 사용자의 질문에 B 부서 문서가 인용되면 안 되므로, 인용 출처도 권한 필터를 거친 것만 렌더링**해야 합니다.

**④ 로깅·모니터링에서의 유출**

Sentry가 가장 흔한 구멍입니다.

- `beforeSend`에서 요청 본문·응답 본문 제거 또는 마스킹
- Session Replay 사용 시 텍스트 마스킹 기본값 유지, 채팅 영역은 명시적으로 `data-sentry-mask`
- 에러 메시지에 대화 내용이나 사내 문서 조각이 섞여 들어가지 않게 커스텀 에러 객체로 감싸기
- 스트리밍 응답 전문을 `console.log`로 찍는 디버깅 코드가 프로덕션에 남지 않도록 린트 규칙

**⑤ 기타**

CSP 헤더 설정, 파일 다운로드 시 `Content-Disposition`과 확장자 검증, 민감 입력 필드의 `autocomplete="off"`, 대화 내용이 브라우저 캐시에 남지 않도록 `Cache-Control` 설정 정도를 짧게 덧붙입니다.

> 랭코드는 그 문제를 **제품 차원에서** 풀고 있다고 느꼈습니다. 특히 대표님 인터뷰에서 '표준을 따르지 않는 기존 기업 시스템에 붙이는 게 진짜 어려운 지점'이라고 하신 부분이, 데모는 되는데 현업에서는 안 돌아가는 문제를 정확히 짚고 있다고 생각했습니다.
>
> 기여할 수 있는 부분은 세 가지입니다. 하나는 **실시간 UI의 렌더링 성능** — 입원 차트에서 표 전체가 재렌더되던 걸 프로파일링으로 원인을 찾아 행 단위로 줄인 경험이, 스트리밍 응답 화면과 같은 문제라고 봅니다. 둘째는 **배포·운영 환경** — 현재 서비스를 GitHub Actions에서 OIDC로 Azure에 로그인해 Blob Storage에 배포하고 있고, PWA 서비스워커가 구버전에 갇히는 문제 때문에 HTML과 sw.js만 캐시를 분리해 올리도록 만들어뒀습니다. 셋째는 **다국어** — 최근 프로젝트에서 번역 누락과 미해결 키, 비-ko 로케일의 한글 잔존을 빌드와 CI에서 차단하고, 번역가와는 스프레드시트로 주고받는 파이프라인을 만들었습니다. 랭코드가 2026년 해외 SaaS 진출을 준비 중이라고 봐서, 이 부분이 바로 쓰일 수 있을 것 같습니다.
>
> 반대로 **C#과 ASP.NET Core는 실무로 다뤄본 적이 없습니다.** 다만 Spring Boot로 Controller-Service-Repository와 DI를 직접 설계해봤고, 새 프레임워크를 캐치업하는 방식 자체가 — 작게 만들고, 테스트로 검증하고, 왜 그렇게 동작하는지 직접 읽는 — 이 회사가 공통사항에 적어두신 워크플로우와 같기 때문에 빠르게 채울 수 있다고 생각합니다."
