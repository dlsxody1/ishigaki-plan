# 🤖 AI 활용 개발 경험 정리

🧭 [[index\|🎯 면접 대비 홈]] · [[면접준비/프로젝트별-꼬리질문\|📋 프로젝트별 꼬리질문]] · [[면접준비/기술질문\|🧠 기술 질문]]

> [!warning] 이 문서 사용법
> 아래 내용은 이력서에 적힌 사실을 뼈대로, 면접에서 풀어 말할 수 있도록 구조화한 것입니다. `> 채워넣기:`로 표시된 부분은 반드시 본인 경험(정확한 수치, 실제 겪은 사례, 구현 디테일)으로 채워야 합니다. 면접관은 "실제로 겪은 디테일"이 있는지 없는지를 꼬리질문으로 바로 확인합니다.

---

## 🧭 왜 이 이야기가 중요한가

2026년 현재 "AI를 쓴다"는 사실 자체는 차별점이 아닙니다. 면접에서 통하는 지점은 **AI가 만든 결과물을 어떻게 신뢰할 수 있는 상태로 관리했는가**입니다. 나의 핵심 메시지는 한 문장으로 이렇게 정리됩니다.

> **"AI 코드 생성이 늘어날수록, 규칙을 사람이 기억하고 리뷰로 잡아내는 게 아니라 도구가 강제하도록 만들었다."**

이 한 문장을 중심에 두고, 아래 4가지 영역이 전부 이 원칙의 구체적인 실행 사례라는 걸 연결해서 말하면 됩니다.

1. 프로젝트 구조·규칙을 문서화 (CLAUDE.md)
2. 문서만으로는 안 지켜지니 **커스텀 린트 훅**으로 강제
3. 한 프롬프트에 다 맡기는 방식의 한계를 겪고 **서브에이전트로 역할 분리**
4. 팀 간 정보 단절 문제를 **공유 컨텍스트 레포지토리(MCP 연동)**로 해결

---

## 1️⃣ 프로젝트 구조·개발 규칙 문서화 (CLAUDE.md)

**있는 그대로 (이력서 기반)**
- AI 코드 생성이 늘면서 FSD(Feature-Sliced Design) 경계가 무너지는 문제 발생
- 프로젝트 구조·개발 규칙을 문서화해 AI가 코드를 생성할 때 참고하도록 함

**왜 문서화만으로는 부족했는가**
- 문서는 AI가 "참고"할 수는 있어도 "강제"하지는 못함 — 컨텍스트 윈도우, 프롬프트 구성에 따라 규칙을 놓치는 경우가 실제로 발생
- 그래서 2️⃣ 린트 훅으로 이어짐 (문서 = 의도·배경 설명, 훅 = 실제 강제 장치라는 역할 분담)

> 채워넣기: CLAUDE.md에 실제로 어떤 항목들을 적었는지 (예: 레이어별 import 규칙, 네이밍 컨벤션, 폴더 구조 예시, 금지 패턴 목록 등) 3~4개 정도 구체적으로 기억해두기

---

## 2️⃣ AI 코드 생성 가드레일 — 커스텀 린트 훅

**있는 그대로 (이력서 기반)**
- 파일 수정 시점에 동작하는 커스텀 린트 훅 도입
- 구조 위반 7종을 **리뷰 대신 훅이 커밋 전에 자동 차단**

**말할 때 강조할 구조 (문제 → 판단 → 해결 → 결과)**
- **문제**: AI가 생성한 코드가 FSD 레이어 경계를 넘어 import하는 일이 반복됨 → 사람이 매 PR마다 리뷰로 잡아내야 했음 → 반복 작업이고 놓치기 쉬움
- **판단**: "반복적이고 규칙이 명확한 문제는 사람이 아니라 도구가 잡아야 한다"는 원칙 — AI 코드 생성 시대에 리뷰어의 역할을 재정의한 셈
- **해결**: 파일 저장/커밋 시점에 실행되는 훅을 만들어 위반 패턴 7종을 정적으로 검사
- **결과**: 구조 위반이 리뷰 단계가 아니라 커밋 전에 차단됨 → 리뷰어가 "구조가 맞는지"보다 "로직이 맞는지"에 집중할 수 있게 됨

> 채워넣기:
> - 정확한 구현 방식 (husky pre-commit? lint-staged? 자체 Node 스크립트로 AST 파싱?)
> - 7종 위반 목록을 실제로 나열할 수 있어야 함 (예: 하위→상위 레이어 import, 다른 슬라이스 내부 파일 직접 참조, 순환 참조, index 파일 우회, shared 레이어에 비즈니스 로직 포함 등 — 본인이 만든 실제 규칙으로 교체)
> - 오탐(false positive) 처리 경험이 있다면 사례 하나

## 3️⃣ 에이전트 역할 분리 — 슬래시 커맨드 9종 · 스킬 13종

**있는 그대로 (이력서 기반)**
- 한 프롬프트에 모든 작업(성능 측정, 스타일링, UX 리뷰 등)을 맡기던 방식 → 결과 일관성이 떨어지고 매번 같은 기준을 재설명해야 하는 문제
- 성능 측정 / 스타일링 / UX 리뷰를 각각 담당하는 서브에이전트로 분리
- 슬래시 커맨드 9종, 스킬 13종 구축
- 디자인 토큰, 보호자 동의 플로우 등 반복 기준을 UX 리뷰 스킬에 내장 → 매번 재설명 없이 재사용

**말할 때 강조할 구조**
- **문제 인식**: "한 프롬프트 = 한 역할"이 아니면 AI 출력의 예측 가능성이 떨어진다는 걸 실무에서 체감 (내가 중요하게 생각하는 코드 품질 기준인 '예측 가능성'과 동일한 원리를 AI 활용에도 적용한 것)
- **설계**: 역할별로 에이전트를 나누고, 각 역할이 반복적으로 참조해야 하는 기준(디자인 토큰, 도메인 규칙 등)을 스킬 형태로 내장
- **효과**: "매번 처음부터 설명하지 않아도 되는" 재사용 가능한 작업 단위를 팀에 제공

> 채워넣기:
> - 슬래시 커맨드 9종 중 대표적인 3~4개 이름과 역할 (예: `/perf-check`, `/style-review`, `/ux-review` 같은 식으로 실제 이름 기억해두기)
> - 스킬 13종 중 가장 자주 쓰인 스킬 2~3개와 실제로 어떤 반복 작업을 줄여줬는지
> - "보호자 동의 플로우"처럼 도메인 특화 규칙을 스킬에 어떻게 내장했는지 구체적 예시

---

## 4️⃣ 팀 간 컨텍스트 공유 (MCP 연동)

**있는 그대로 (이력서 기반)**
- 인프라·백엔드·ML 팀과 협업 시 정보를 매번 수동으로 옮기던 문제
- 공유 레포지토리의 inbox, 공용 컨텍스트, 의사결정 로그로 전환
- 프론트엔드 프로젝트와 연결해 **사내 5개 프로젝트가 같은 작업 정보를 참조**

**말할 때 강조할 구조**
- **문제**: 팀마다 다른 도구(Slack, Notion, 각자의 레포)를 쓰다 보니 같은 정보를 여러 번 설명해야 하고, 의사결정 배경이 유실됨
- **해결**: 코드와 같은 공간(레포지토리)에 inbox(들어오는 요청/이슈), 공용 컨텍스트(현재 상태), 의사결정 로그(왜 그렇게 결정했는지)를 구조화
- **AI와의 연결고리**: 이 구조를 MCP로 에이전트가 직접 읽고 쓸 수 있게 연결 — 사람이 매번 컨텍스트를 복사-붙여넣기 하지 않아도 에이전트가 최신 의사결정 배경을 참조 가능
- **결과**: 사내 5개 프로젝트가 같은 작업 정보를 참조하는 구조로 확장됨

> 채워넣기:
> - MCP를 정확히 어떤 방식으로 연결했는지 (자체 MCP 서버를 만들었는지, 기존 도구의 MCP를 붙였는지)
> - inbox·공용 컨텍스트·의사결정 로그가 실제로 어떤 파일/폴더 구조인지
> - 접근 권한·최신성 관리를 어떻게 했는지 (이전에 나온 꼬리질문이기도 함)

## 🗣️ 하나의 스토리로 말하는 법 (30초 요약 스크립트 예시)

> "저는 AI 코드 생성이 늘어날수록 사람이 규칙을 기억하는 방식은 한계가 있다고 봤습니다. 그래서 프로젝트 구조를 문서화하는 데서 그치지 않고, 파일 수정 시점에 동작하는 커스텀 린트 훅을 만들어 구조 위반 7종을 커밋 전에 자동으로 막았습니다. 또 한 프롬프트에 모든 작업을 맡기면 결과가 들쭉날쭉하다는 걸 겪고 나서, 성능 측정·스타일링·UX 리뷰를 각각 전담하는 서브에이전트로 역할을 나누고 슬래시 커맨드 9종, 스킬 13종을 구축했습니다. 마지막으로 팀 간 정보 단절 문제는 공유 레포지토리에 inbox·공용 컨텍스트·의사결정 로그를 두고 MCP로 연결해서, 사내 5개 프로젝트가 같은 작업 정보를 참조하도록 만들었습니다."

이 스크립트를 뼈대로 두고, 면접관이 파고드는 지점(구현 디테일, 실패 사례, 대안 검토)에 따라 위 1~4번 섹션의 "채워넣기" 내용으로 답변을 확장하면 됩니다.

## ❓ 추가 예상 질문

**Q. AI 도구를 도입하면서 팀원들의 저항은 없었나요? 어떻게 설득했나요?**
- > 채워넣기: 실제로 저항이 있었다면 어떻게 대응했는지, 없었다면 왜 자연스럽게 받아들여졌는지

**Q. 이 모든 장치(린트 훅, 서브에이전트, 공유 레포)를 혼자 만들었나요, 팀과 함께 만들었나요?**
- 역할 분담을 명확히 답변 준비 (본인이 주도한 부분과 팀이 함께한 부분 구분)

**Q. AI가 만든 코드와 사람이 짠 코드를 구분해서 관리하나요? 커밋에 AI 생성 여부를 남기나요?**
- > 채워넣기: 실제 정책이 있다면 설명, 없다면 본인 의견 준비

**Q. 이 경험을 우리 회사/팀에 적용한다면 어떤 부분부터 시작하고 싶나요?**
- 회사별 맞춤 답변이 필요한 질문 — 지원하는 회사의 기술 스택·조직 규모를 고려해 "가장 반복적이고 규칙이 명확한 부분부터 도구화"한다는 원칙으로 답변 준비

**Q. 커스텀 린트 훅이나 서브에이전트 체계가 실패했거나 기대만큼 효과가 없었던 부분은 없었나요?**
- 완벽한 성공 스토리보다 한계를 인정하고 개선 방향을 제시하는 답변이 더 신뢰를 줌
- > 채워넣기: 실제 한계/실패 경험 하나는 꼭 준비해두기 (없다면 "지금 돌아보면 이렇게 했을 것 같다"는 회고형 답변도 가능)
