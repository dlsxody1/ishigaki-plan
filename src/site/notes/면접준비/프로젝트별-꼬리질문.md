## 🐾 VitalVET · 동물병원 임상 SaaS (2026.01 ~ 2026.07)

### 입원 차트 재렌더 범위 축소

**Q. React.memo로 재렌더 범위를 줄였다고 했는데, memo만으로 해결됐나요? props가 매번 새 객체/배열이면 memo가 무력화되지 않나요?**
- 행에 내려주는 콜백을 `useCallback`으로 안정화하고, 행 데이터 자체도 참조가 불필요하게 바뀌지 않도록 정리했다는 흐름으로 설명
- 단순히 `memo`를 씌운 게 아니라 "무엇이 참조를 바꾸고 있었는지"를 먼저 프로파일링(React DevTools Profiler)으로 확인했다는 과정을 강조
- 대안으로 고려했던 것(행 단위 상태 분리, 가상화 라이브러리 도입)과 왜 그 방법을 택하지 않았는지 — 최소 변경으로 문제를 해결했다는 판단 기준
- > 채워넣기: 실제 프로파일링 도구/과정, 대안 검토 여부

**Q. 표 전체가 아니라 "행 하나"로 재렌더가 줄었다는 걸 어떻게 측정하고 검증했나요?**
- React DevTools Profiler의 flamegraph에서 렌더된 컴포넌트 수/시간 비교, 또는 `why-did-you-render` 류 도구 사용 경험이 있다면 언급
- 수치가 없다면 "커밋 전/후 렌더 트리 스크린샷으로 비교" 같은 실제 검증 방법을 구체적으로 답변 준비
- > 채워넣기: 실제 측정 수치/방법

### 흩어진 결제 폼 상태 통합

**Q. react-hook-form과 zod를 선택한 이유는? Formik이나 직접 useState로 관리하는 것과 비교하면?**
- 비제어(uncontrolled) 방식이라 입력마다 리렌더가 발생하지 않는 성능 이점, 진료 중 빠른 입력이 중요한 화면과 맞아떨어짐
- zod는 런타임 검증 + TypeScript 타입 추론(`z.infer`)을 동시에 얻을 수 있어 스키마와 타입이 어긋나는 문제를 줄임
- Formik 대비 번들 크기·API 단순성, 결제처럼 검증 규칙이 복잡한 폼에서 `resolver` 패턴으로 확장하기 쉬웠던 점

### AI 코드 생성 가드레일

**Q. "구조 위반 7종을 커밋 전에 차단"하는 린트 훅, 실제로 어떻게 구현했나요? 어떤 위반들을 잡아내나요?**
- 구현 방식(예: husky pre-commit + 커스텀 ESLint 규칙 / 자체 스크립트로 FSD 레이어 import 경로 파싱) 구체적으로 설명할 수 있어야 함
- 대표적인 위반 예시: 하위 레이어에서 상위 레이어 import, 다른 feature/entity 내부 파일 직접 import(공개 API 우회), 순환 참조 등
- "왜 리뷰가 아니라 훅으로 자동화했는가" — 사람이 반복적으로 놓치는 규칙일수록 도구화하는 게 낫다는 원칙 강조
- 오탐(false positive) 대응은 어떻게 했는지도 준비 (예외 처리 규칙, 화이트리스트)
- > 채워넣기: 정확한 구현 방식, 7종 위반의 구체적 목록

**Q. 서브에이전트를 "성능/스타일링/UX 리뷰"로 나눴다고 했는데, 이걸 실제 개발 워크플로우에 어떻게 붙였나요? 결과물 품질은 어떻게 검증했나요?**
- 하나의 프롬프트에 모든 맥락을 담으면 결과가 매번 달라지는 문제(예측 가능성 저하)를 지적
- 각 에이전트가 참조하는 기준(디자인 토큰, 보호자 동의 플로우 등)을 스킬에 내장해 "매번 재설명하지 않아도 되는" 재사용성 확보 과정
- 결과물 검증은 결국 사람이 리뷰하되, 반복적인 체크리스트성 항목만 자동화했다는 선을 명확히 답변
- (자세한 구조는 [[면접준비/AI-활용-경험\|AI-활용-경험]] 참고)

### 팀 간 컨텍스트 공유

**Q. 공유 레포지토리의 inbox·공용 컨텍스트·의사결정 로그는 구체적으로 어떤 구조인가요? 접근 권한이나 최신성은 어떻게 관리했나요?**

## 🏢 MetaDX 기업 홈페이지 · Core Web Vitals 개선 (2025.08 ~ 2026.05)

**Q. 이미지 로딩 시간 30% 감소, 어떤 지표를 기준으로 측정했나요? LCP에는 얼마나 영향을 줬나요?**
- 측정 도구(Lighthouse, WebPageTest, Chrome DevTools Network 탭 등)와 Before/After 수치를 준비
- 대표 이미지가 보통 LCP 요소였다면 `fetchPriority="high"` 적용이 LCP 개선과 직결된다는 논리로 설명
- WebP 변환이 파일 크기·디코딩 시간에 준 영향까지 언급하면 좋음(AVIF는 왜 안 썼는지도 대비)
- > 채워넣기: Lighthouse Before/After 점수, LCP 실제 수치

**Q. 스크롤 시 상태 대신 useRef + data attribute를 쓴 이유는? 왜 상태 관리로는 안 되나요?**
- React state 변경은 리렌더를 트리거하므로, 매 스크롤 이벤트(고빈도)마다 상태를 갱신하면 렌더 비용이 커진다는 원리 설명
- `useRef`로 DOM에 직접 접근해 CSS만 갱신(data attribute → CSS selector)하면 React 렌더 사이클을 건너뛸 수 있다는 점
- 스크롤 이벤트 자체의 쓰로틀/디바운스, 또는 `passive: true` 리스너 적용 여부도 준비해두면 좋음

**Q. SPA인데 왜 SSR을 안 하고 prerender(SSG)를 택했나요? 두 방식의 차이와 트레이드오프는?**
- 기업 홈페이지처럼 콘텐츠가 자주 안 바뀌는 페이지엔 빌드 타임에 미리 렌더링하는 prerender가 서버 유지비용 없이 SEO 문제를 해결할 수 있다는 점
- SSR은 매 요청마다 서버 렌더링 비용이 들고 인프라가 필요하지만 실시간 데이터에 강함 — 이 프로젝트엔 과했다는 판단 근거
- `hreflang`과 다국어 정적 HTML을 S3에 업로드하는 구조를 그림으로 설명할 수 있으면 좋음

## 🗂️ MetaDx Office · 사내 전자결재와 경비 관리 (2025.05 ~ 2026.07)

**Q. 단위 테스트 25개, 어떤 기준으로 이 로직들을 골랐나요? 커버리지 목표는 없었나요?**
- "오류가 나면 결재 건 전체에 영향을 주는 로직" 우선순위로 골랐다는 기준(상태머신, 인증/인터셉터, 금액 규칙, 스키마) — 커버리지 %보다 리스크 기반 테스트 전략이었음을 강조
- 전체 커버리지 수치가 없다면 그것도 솔직히 답하고, 왜 전면 커버리지보다 리스크 우선이 합리적이었는지 논리로 방어

**Q. steiger로 FSD 레이어 의존성을 검사한다고 했는데, CI에서 실패하면 어떻게 되나요? 실제로 위반이 잡힌 사례가 있나요?**
- CI 파이프라인 단계(빌드 전/후 어디에 배치했는지), 실패 시 머지 차단 여부
- 구체적인 위반 사례 하나 정도는 스토리로 준비해두면 설득력이 큼 (어떤 레이어를 어떻게 잘못 참조했고, 어떻게 고쳤는지)
- > 채워넣기: 실제 위반 사례 하나

**Q. 401 인터셉터와 인증 가드는 구체적으로 어떻게 구현했나요? 토큰 갱신(refresh) 흐름은 어떻게 처리했나요?**
- Axios/fetch 인터셉터에서 401 감지 → refresh token 요청 → 원래 요청 재시도 흐름을 그림/순서로 설명할 수 있어야 함
- 동시에 여러 요청이 401을 받았을 때 refresh를 한 번만 호출하도록 막는 처리(큐잉/락) 여부도 준비

## 🧬 CancerVET · 진단 리포트 자동 생성 파이프라인 (2025.01 ~ 2025.05)

**Q. HTML/CSS로 만든 화면을 Playwright로 PDF 변환하는 방식, 왜 이 방법을 택했나요?**
- 프론트엔드 기술(HTML/CSS)을 그대로 재사용해 레이아웃 유지보수 비용을 낮췄다는 점
- reportlab 같은 PDF 전용 라이브러리는 세밀한 레이아웃 제어가 번거롭고, 웹 기술 대비 학습/유지보수 비용이 크다는 비교
- Playwright 렌더링 비용(헤드리스 브라우저 구동)이 서버 리소스에 미친 영향, 동시 요청 처리 방식도 대비

**Q. 로컬과 Linux 컨테이너의 한글 폰트 불일치 문제, 정확히 어떤 증상이었고 왜 웹폰트 포함이 근본 해결책이었나요?**
- 컨테이너 이미지에 한글 폰트가 설치돼 있지 않아 시스템 폰트로 대체 렌더링되며 줄바꿈·자간이 로컬과 달라지는 증상 설명
- 시스템 폰트 설치 대신 웹폰트(파일 내장/CDN)로 못박아 환경 의존성을 없앤 이유

**Q. AWS Lambda·S3 구조를 FastAPI 서버로 통합한 이유는? Lambda의 어떤 점이 불편했나요?**
- Lambda 콜드 스타트, 여러 함수 간 상태·설정 공유의 어려움, 배포/디버깅 복잡도 등 실제 겪은 불편함 위주로 답변 준비
- FastAPI로 통합하면서 얻은 것(로컬 재현 용이성, 로깅/모니터링 일원화)과 잃은 것(서버리스의 자동 스케일링)까지 균형 있게

## 📁 퀀텀에이아이 · 문서관리 시스템 (2022.11 ~ 2023.03)

**Q. Controller-Service-Repository 구조로 CRUD API를 만들었다고 했는데, 각 계층의 책임을 어떻게 나눴나요?**
- Controller: 요청/응답 형식과 검증, Service: 비즈니스 로직, Repository: 데이터 접근 — 계층을 넘나드는 의존을 어떻게 막았는지
- 이 경험이 지금 FSD로 프론트엔드 레이어를 나누는 감각과 어떻게 이어지는지 연결해서 답하면 좋은 인상

**Q. 문서에서 텍스트를 추출·요약해 청구 입력값으로 연결했다고 했는데, 추출/요약은 어떤 방식으로 했나요? 정확도는 어떻게 검증했나요?**
- OCR/텍스트 파싱 방식(라이브러리, 규칙 기반 vs 모델 기반)과 실패 케이스 처리(사람 검수 단계 유무)
- 정확도가 낮았던 케이스와 어떻게 보완했는지 — 완벽하지 않았다면 한계를 솔직히 인정하고 개선 아이디어로 마무리
- > 채워넣기: 실제 사용한 추출 방식
