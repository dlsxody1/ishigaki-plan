## ⚛️ React · 렌더링 최적화

**Q. React가 리렌더를 결정하는 기준은? state가 바뀌면 왜 자식까지 다시 렌더되나요?**
- 부모가 리렌더되면 기본적으로 자식도 함께 리렌더(reconciliation 과정에서 재실행) — `memo`가 이 흐름을 막는 방법이라는 연결

**Q. useMemo/useCallback을 남용하면 오히려 안 좋은 이유는?**
- 메모이제이션 자체도 이전 값 비교·저장 비용이 있어, 계산이 가벼운 값까지 감싸면 오히려 오버헤드가 커질 수 있음
- 실제로 병목을 프로파일링해 확인 후 적용하는 습관을 강조

**Q. React의 key prop은 왜 필요한가요? index를 key로 쓰면 어떤 문제가 생기나요?**
- key로 이전/이후 리스트의 엘리먼트를 매칭해 불필요한 DOM 재생성을 막음 — 리스트 순서가 바뀌거나 항목이 삭제/삽입될 때 index를 key로 쓰면 잘못된 엘리먼트에 상태가 남는 문제

**Q. React 18/19의 concurrent 렌더링, useTransition/useDeferredValue는 언제 쓰나요?**
- 긴급하지 않은 업데이트(예: 필터링된 목록 렌더링)를 낮은 우선순위로 미뤄 입력 반응성을 지키는 용도 — 입원 차트처럼 입력이 잦은 화면과 연결지어 설명 가능

**Q. 가상 DOM이 항상 실제 DOM 조작보다 빠른가요?**
- 아니오 — 작은 규모 변경에는 직접 DOM 조작이 더 빠를 수 있음. 가상 DOM의 가치는 "속도"가 아니라 선언적 UI와 일관된 업데이트 모델이라는 점을 짚기

**Q. 리스트가 수천 개 이상일 때 어떻게 렌더링을 최적화하나요?**
- 가상화(virtualization, react-window/react-virtual)로 화면에 보이는 항목만 렌더링 — 실제 적용 경험이 있다면 구체적 사례로

## 🔷 TypeScript

**Q. interface와 type의 차이는? 언제 무엇을 쓰나요?**
- interface는 선언 병합(declaration merging) 가능, type은 유니온/교차 타입 등 더 유연한 표현 — 팀 컨벤션에 따라 선택 기준 설명

**Q. zod 스키마에서 타입을 추론(z.infer)해서 쓰는 방식과, 타입을 먼저 정의하고 검증 로직을 따로 짜는 방식의 차이는?**
- 스키마를 단일 진실 공급원(single source of truth)으로 두면 타입과 런타임 검증이 어긋날 여지가 없음 — 실제 프로젝트에서 이 방식을 택한 이유로 연결

**Q. unknown과 any의 차이는? 왜 any 대신 unknown을 쓰라고 하나요?**
- unknown은 사용 전 타입 좁히기(narrowing)를 강제해 타입 안전성을 유지, any는 타입 체크를 완전히 우회

**Q. 제네릭은 왜 쓰나요? 실제로 어떤 상황에서 써봤나요?**
- 재사용 가능한 컴포넌트/훅에서 타입을 특정하지 않고 호출부에서 결정하도록 — 예: 공용 API 훅, 테이블 컴포넌트 등 실제 사례로 답변 준비

**Q. 타입 좁히기(narrowing)는 어떤 방식들이 있나요?**
- typeof, instanceof, in 연산자, 사용자 정의 타입 가드 함수(`is` 반환) 등

## 🧩 상태 관리 · 폼

**Q. TanStack Query(서버 상태)와 Jotai(클라이언트 상태)를 왜 나눠서 쓰나요? 하나로 통합할 수는 없나요?**
- 서버 상태는 캐싱·재검증·동기화가 필요한 "원격 데이터의 로컬 복사본"이고, 클라이언트 상태는 UI 자체의 상태 — 성격이 달라 전용 도구를 쓰는 게 코드가 단순해짐

**Q. TanStack Query의 캐시 무효화(invalidation) 전략은 어떻게 가져가나요? staleTime과 cacheTime(gcTime)의 차이는?**
- staleTime: 데이터를 신선하다고 간주하는 기간(재요청 안 함), gcTime: 캐시가 메모리에서 사라지기까지의 시간 — 실제 프로젝트에서 어떤 값을 썼고 왜인지

**Q. Jotai를 Redux나 Zustand 대신 선택한 이유는?**
- atom 단위로 상태를 쪼개 필요한 컴포넌트만 구독하게 해 불필요한 리렌더를 줄일 수 있음, 보일러플레이트가 적음 — 프로젝트 규모/팀 컨벤션과 연결해 설명

**Q. react-hook-form은 왜 "비제어" 방식이 기본이고, 그게 왜 성능에 유리한가요?**
- 각 입력을 ref로 직접 관리해 입력할 때마다 리렌더를 트리거하지 않음 — 제어 컴포넌트(useState 기반) 대비 대규모 폼에서 유리

**Q. 폼 검증을 서버와 클라이언트 양쪽에서 하는 이유는? 중복 아닌가요?**
- 클라이언트 검증은 UX(즉각 피드백), 서버 검증은 보안·데이터 무결성의 최종 방어선 — 클라이언트 검증만 믿을 수 없는 이유(우회 가능)

## 🏗️ 아키텍처 · FSD

**Q. FSD(Feature-Sliced Design)를 한 문장으로 설명한다면? 기존 폴더 구조와 뭐가 다른가요?**
- 레이어(app-pages-features-entities-shared)에 위계질서를 두고 상위만 하위를 참조하게 강제하는 구조 — 컨테이너/프리젠터 패턴처럼 "이유 없이 깊어지는" 구조를 방지

**Q. features와 entities의 경계가 애매할 때 어떻게 판단하나요?**
- entities는 "무엇인가"(비즈니스 데이터 모델), features는 "무엇을 하는가"(사용자 시나리오) — 실제로 판단이 어려웠던 사례가 있다면 준비

**Q. index 파일로 public API를 캡슐화한다는 게 정확히 무슨 의미인가요?**
- 슬라이스 내부 파일을 다른 곳에서 직접 import하지 못하게 하고, index.ts가 노출하는 것만 쓰게 강제 — 내부 구현을 바꿔도 외부 영향이 없는 결합도 낮은 구조

**Q. FSD가 오히려 과할 수 있는 프로젝트 규모나 상황이 있을까요?**
- 작은 사이드 프로젝트나 MVP 단계에선 레이어를 나누는 비용이 이득보다 클 수 있음 — "언제 구조를 도입할지"에 대한 본인 기준을 준비해두면 좋은 인상

## 🧪 테스트 · 품질

**Q. 단위 테스트와 통합 테스트, 어떤 기준으로 우선순위를 정하나요?**
- 실패 시 파급력이 큰 로직(결재 상태머신, 인증 등) 우선, UI는 스냅샷보다 사용자 행동 기반(Testing Library) 테스트를 선호한다는 원칙

**Q. Testing Library는 왜 구현이 아니라 "사용자 관점"으로 테스트하라고 하나요?**
- 내부 구현이 바뀌어도(리팩터링) 테스트가 깨지지 않게 하기 위해 — 텍스트/role 기반 쿼리로 실제 사용자가 보는 방식대로 검증

**Q. CI에 tsc·린트·빌드·테스트를 다 넣으면 느려지지 않나요? 어떻게 관리했나요?**
- 캐싱(node_modules, 빌드 캐시), 변경된 파일 기준 부분 실행, 병렬 실행 등 실제 적용했거나 고려한 방법

**Q. 테스트 커버리지가 높다고 버그가 없는 건 아닌데, 커버리지를 어떻게 바라보나요?**
- 커버리지는 "테스트가 실행된 비율"일 뿐 품질 지표가 아님 — 리스크 기반으로 무엇을 테스트할지 판단하는 게 더 중요하다는 본인 관점

## ⚡ 성능 · Core Web Vitals

**Q. LCP, CLS, INP(구 FID)는 각각 무엇을 측정하고, 어떻게 개선하나요?**
- LCP: 가장 큰 콘텐츠 렌더 시점(이미지 우선순위·서버 응답 개선), CLS: 레이아웃 밀림(이미지/폰트에 크기 미리 지정), INP: 상호작용 응답성(무거운 JS 실행 분할)

**Q. 코드 스플리팅은 어떤 기준으로 나누나요? 라우트 단위 vs 컴포넌트 단위**
- 라우트 단위가 기본, 무거운 라이브러리(차트, 에디터 등)는 사용 시점에 동적 import로 컴포넌트 단위 분할

**Q. 이미지 최적화에서 WebP/AVIF 외에 고려할 수 있는 것들은?**
- srcset/sizes로 반응형 이미지 제공, CDN 캐싱, 적절한 해상도로 원본 리사이즈, blur-up placeholder 등

**Q. 번들 크기를 어떻게 분석하고 줄이나요?**
- 번들 분석 도구(rollup-plugin-visualizer 등)로 큰 의존성 파악, tree shaking이 안 되는 라이브러리 대체, 중복 의존성 제거

## 🌐 브라우저 · 네트워크 기초

**Q. 브라우저 렌더링 과정(파싱 → 렌더 트리 → 레이아웃 → 페인트)을 설명해보세요.**
- HTML/CSS 파싱해 DOM/CSSOM 생성 → 렌더 트리 결합 → 레이아웃(각 요소 위치·크기 계산) → 페인트/합성(GPU) 순서

**Q. CORS는 왜 발생하고 어떻게 해결하나요?**
- 브라우저의 동일 출처 정책(SOP) 때문 — 서버에서 Access-Control-Allow-Origin 등 CORS 헤더로 허용, 프리플라이트(OPTIONS) 요청 개념도 함께 설명

**Q. 401 인터셉터를 설계할 때 401과 403의 차이는 어떻게 구분해서 처리하나요?**
- 401: 인증 안 됨(토큰 만료/부재) → 재로그인/토큰 갱신, 403: 인증은 됐지만 권한 없음 → 접근 거부 안내로 분기 처리

**Q. XSS와 CSRF의 차이와 프론트엔드에서의 방어 방법은?**
- XSS: 악성 스크립트 삽입 → 사용자 입력 이스케이프, dangerouslySetInnerHTML 최소화. CSRF: 인증된 세션으로 원치 않는 요청 → CSRF 토큰, SameSite 쿠키
