## 1. 제어 컴포넌트 vs 비제어 컴포넌트 (Controlled / Uncontrolled Components)

**정의**
- **제어 컴포넌트**: `<input value={state} onChange={...}>`처럼 폼 요소의 값을 React state가 소유하는 방식. "Single Source of Truth"가 React 상태에 있음.
- **비제어 컴포넌트**: `<input ref={inputRef}>`처럼 값을 DOM 자신이 들고 있고, 필요할 때만 `ref.current.value`로 꺼내오는 방식. React state가 값의 주인이 아님.

**동작 원리**
- 제어 컴포넌트는 사용자가 키를 하나 입력할 때마다 `onChange` → `setState` → 리렌더가 발생합니다. state가 바뀌었으니 해당 컴포넌트(+ 그 자식들)가 다시 렌더 함수를 실행합니다.
- 비제어 컴포넌트는 입력값이 **브라우저 네이티브 DOM 요소 내부**에만 저장됩니다. React는 이 값의 변화를 모르고, 렌더 트리거도 발생하지 않습니다. 값을 읽어야 할 때(제출 시점 등)만 ref를 통해 DOM에서 직접 값을 꺼내옵니다.
- `react-hook-form`은 각 `<input>`을 `register()`로 감싸 내부적으로 ref를 등록하고, 값 변화는 구독(subscribe) 패턴으로만 필요한 곳에 전파합니다. 즉 "입력 → 리렌더"의 연결고리를 끊어버리는 게 핵심입니다.

**코드로 비교**
```tsx
// 제어 컴포넌트 — 매 키 입력마다 이 컴포넌트가 리렌더됨
function ControlledInput() {
  const [value, setValue] = useState("");
  return <input value={value} onChange={(e) => setValue(e.target.value)} />;
}

// 비제어 컴포넌트 — 입력해도 이 컴포넌트는 리렌더되지 않음
function UncontrolledInput() {
  const ref = useRef<HTMLInputElement>(null);
  const handleSubmit = () => console.log(ref.current?.value);
  return <input ref={ref} />;
}
```

**내 프로젝트와의 연결 (VitalVET 결제 폼)**
- 결제 폼처럼 필드가 많고 진료 중 빠르게 입력해야 하는 화면에서, 제어 방식이면 필드 하나 값이 바뀔 때마다 폼 전체(혹은 해당 서브트리)가 리렌더될 수 있음.
- `react-hook-form`으로 비제어 방식을 쓰면 각 입력이 리렌더를 유발하지 않고, 검증(`zod` resolver)은 제출 시점이나 blur 시점에만 실행되도록 제어 가능 → 입력 반응성이 중요한 화면에 유리.

**흔한 오해 / 꼬리질문 대비**
- "그럼 실시간으로 다른 필드 값을 보고 조건부 렌더링해야 하면?" → react-hook-form은 `watch()`로 특정 필드만 구독해서 부분적으로 제어 컴포넌트처럼 쓸 수 있음(필요한 곳만 선택적으로 리렌더 발생).
- "비제어가 항상 좋은가?" → 아니오. 값이 변할 때마다 즉시 다른 UI에 반영해야 하는 경우(예: 글자 수 카운터, 실시간 유효성 하이라이트)는 제어 방식이나 `watch()`가 필요. 트레이드오프 문제이지 무조건적인 정답은 없음.

## 2. React.memo와 얕은 비교 (Shallow Comparison)

**정의**: 컴포넌트를 `memo()`로 감싸면, 부모가 리렌더돼도 **props가 이전과 같으면** 해당 컴포넌트는 렌더를 건너뜁니다.

**동작 원리**
- React는 기본적으로 부모가 리렌더되면 자식도 무조건 다시 렌더 함수를 호출합니다(이게 기본 동작).
- `memo`는 이전 props와 새 props를 **얕은 비교(Object.is 기반, 1단계 깊이만)** 해서 모든 값이 같으면 이전 렌더 결과(가상 DOM)를 재사용합니다.
- 함정: 객체/배열/함수는 내용이 같아도 매 렌더마다 "새로운 참조"로 생성되면 얕은 비교에서 다르다고 판정됩니다. 그래서 `memo`만 씌우고 콜백을 매번 새로 만들면 무의미해집니다 → `useCallback`/`useMemo`로 참조를 고정해야 `memo`가 실제로 작동합니다.

**코드**
```tsx
const Row = memo(function Row({ item, onUpdate }: RowProps) {
  return <tr onClick={() => onUpdate(item.id)}>{item.value}</tr>;
});

// 부모에서 onUpdate를 매번 새로 만들면 memo가 무력화됨
const onUpdate = useCallback((id: string) => { /* ... */ }, []); // 참조 고정
```

**내 프로젝트와의 연결 (VitalVET 입원 차트)**
- 셀 하나를 수정해도 표 전체가 리렌더되던 원인은, 상위 컴포넌트의 state가 바뀔 때 모든 행 컴포넌트가 같은 부모 아래 있어서 함께 리렌더된 것.
- 행 컴포넌트를 `React.memo`로 감싸고, 행에 내려주는 콜백을 `useCallback`으로 안정화 → 수정된 행만 props가 실제로 바뀌므로 나머지 행은 렌더 스킵.

**흔한 오해**
- "memo를 다 씌우면 빨라지나요?" → 아니오. 비교 자체에도 비용이 있음. props가 자주 바뀌는 컴포넌트에 씌우면 "비교 비용 + 어차피 리렌더" 이중 비용이 됨. 리스트의 반복 요소처럼 "대부분은 props가 안 바뀌는" 상황에 효과적.

## 3. useCallback / useMemo와 참조 동일성 (Referential Equality)

**정의**
- `useCallback(fn, deps)`: deps가 안 바뀌면 이전 함수 참조를 그대로 반환(함수를 메모이제이션).
- `useMemo(calc, deps)`: deps가 안 바뀌면 이전 계산 결과값을 그대로 반환(값을 메모이제이션).

**동작 원리**
- JS에서 `{} === {}`는 `false`입니다. 함수도 마찬가지로 매 렌더마다 새로 정의되면 이전 함수와 다른 참조입니다.
- `useCallback`/`useMemo`는 내부적으로 이전 deps 배열과 새 deps 배열을 얕은 비교해서, 같으면 캐시해둔 이전 참조/값을 그대로 돌려줍니다. React가 이 값을 렌더 사이 유지하기 위해 Fiber 노드에 저장해둡니다.

**언제 실제로 의미가 있는가**
- 그 값/함수가 `memo`로 감싼 자식에게 props로 전달될 때 (참조가 바뀌면 memo가 무력화되므로)
- 의존성 배열(useEffect 등)에 들어가서, 매번 바뀌면 effect가 불필요하게 재실행될 때
- 계산 비용이 실제로 큰 값을 매 렌더마다 재계산하지 않기 위해

**흔한 오해**
- 단순 원시값(문자열, 숫자) 계산이나, 어차피 memo로 안 감싼 컴포넌트에 넘기는 함수까지 감싸는 건 오버엔지니어링. "측정 후 최적화"가 원칙.

## 4. React 재조정(Reconciliation)과 렌더링 파이프라인

**정의**: React가 state/props 변화를 감지했을 때, 실제 DOM을 어떻게, 얼마나 바꿀지 결정하는 과정.

**동작 원리 (간단 버전)**
1. **Render phase**: 컴포넌트 함수를 다시 호출해 새 가상 DOM(엘리먼트 트리)을 만듦. 이 단계는 순수 계산이라 중단/재시작 가능(Concurrent 기능의 기반).
2. **Diffing**: 이전 트리와 새 트리를 비교. 같은 위치의 같은 타입이면 재사용, 타입이 다르면 서브트리 통째로 버리고 새로 생성. 리스트는 `key`로 항목을 식별해서 매칭.
3. **Commit phase**: 실제로 바뀐 부분만 실제 DOM에 반영(이 단계는 동기적, 중단 불가).

**왜 key가 중요한가**
- key가 없거나 index를 key로 쓰면, 리스트 중간에 항목이 삭제/삽입될 때 React가 "어떤 게 어떤 항목인지" 잘못 매칭해서, 엉뚱한 DOM 노드에 이전 상태(입력값, 포커스 등)가 남는 버그가 생김.

**내 프로젝트와의 연결**: `memo` 최적화가 바로 이 diffing 단계에서 "비교조차 하지 않고 건너뛰게" 만드는 장치라는 걸 설명하면, 단순 암기가 아니라 원리를 이해하고 있다는 인상을 줌.

## 5. useRef와 DOM 직접 조작으로 렌더 사이클 우회하기

**정의**: `useRef`로 만든 객체는 `.current` 값이 바뀌어도 **리렌더를 트리거하지 않습니다.** state와 결정적으로 다른 지점.

**동작 원리**
- state는 "값 저장 + 변경 시 리렌더 예약"이 세트지만, ref는 "값 저장"만 함. React가 관리하는 렌더 사이클과 무관하게 값을 유지할 수 있는 탈출구.
- `ref.current`로 실제 DOM 노드에 접근해 `classList.add()`, `setAttribute()` 같은 네이티브 DOM API를 직접 호출하면, React의 render → diff → commit 파이프라인을 아예 거치지 않고 화면을 바꿀 수 있음.

**내 프로젝트와의 연결 (MetaDX 홈페이지 스크롤 헤더)**
- 스크롤 이벤트는 매우 고빈도(초당 수십 번)로 발생. 이걸 state로 관리하면 스크롤할 때마다 React 렌더 사이클이 통째로 돌아감.
- 대신 스크롤 위치를 `useRef`로만 추적하고, 헤더 DOM에 `data-scrolled="true"` 같은 속성을 직접 설정 → CSS `[data-scrolled="true"] { ... }` 셀렉터로 스타일 변경. React 렌더는 한 번도 발생하지 않음.

**코드**
```tsx
function Header() {
  const headerRef = useRef<HTMLElement>(null);
  useEffect(() => {
    const onScroll = () => {
      const scrolled = window.scrollY > 10;
      headerRef.current?.setAttribute("data-scrolled", String(scrolled));
    };
    window.addEventListener("scroll", onScroll, { passive: true });
    return () => window.removeEventListener("scroll", onScroll);
  }, []);
  return <header ref={headerRef} className="header">...</header>;
}
```
- `{ passive: true }`도 같이 언급하면 좋음 — 브라우저에게 "이 리스너는 `preventDefault`를 호출하지 않는다"고 미리 알려줘서, 스크롤 이벤트 처리를 기다리지 않고 즉시 스크롤을 진행시킬 수 있게 하는 성능 힌트.

## 6. zod 스키마와 타입 추론(z.infer) — 스키마 우선 설계

**정의**: zod는 런타임 값 검증 라이브러리이자, `z.infer<typeof schema>`로 TypeScript 타입을 **스키마로부터 자동 생성**할 수 있게 해줌.

**동작 원리**
- 보통은 타입을 먼저 정의하고(`interface User {...}`), 검증 로직을 별도로 짜는데 — 이 둘은 서로 동기화가 깨지기 쉬움(타입은 바꿨는데 검증 로직은 안 바꾸는 실수).
- zod는 스키마 하나를 "단일 진실 공급원(Single Source of Truth)"으로 두고, 타입은 그 스키마에서 자동으로 파생시킴. 컴파일 타임 타입(TypeScript)과 런타임 검증(zod)이 항상 일치하도록 구조적으로 보장.

**코드**
```ts
const PaymentSchema = z.object({
  amount: z.number().positive(),
  method: z.enum(["card", "cash"]),
});
type Payment = z.infer<typeof PaymentSchema>; // { amount: number; method: "card" | "cash" }

// react-hook-form과 결합
const form = useForm<Payment>({ resolver: zodResolver(PaymentSchema) });
```

**내 프로젝트와의 연결**: 결제 폼처럼 검증 규칙이 복잡하고 자주 바뀌는 곳에서, 타입과 검증이 어긋나 생기는 버그(예: 런타임에는 통과하는데 타입은 에러, 혹은 그 반대)를 구조적으로 차단.

**흔한 오해**: "TypeScript 타입만 있으면 안전한 거 아닌가?" → TypeScript는 **컴파일 타임**에만 존재하고 빌드되면 사라짐. API 응답처럼 외부에서 들어오는 값은 런타임에 실제로 그 모양인지 zod 같은 도구로 검증해야 함 — 이게 "타입은 있는데 런타임 검증이 없는" 앱의 흔한 구멍.

## 7. TanStack Query의 캐싱: staleTime vs gcTime, Query Key

**정의**
- **staleTime**: 데이터를 "신선하다"고 간주하는 시간. 이 시간 동안은 같은 쿼리를 다시 요청해도 네트워크 요청 없이 캐시를 즉시 반환.
- **gcTime**(구 cacheTime): 쿼리를 구독하는 컴포넌트가 하나도 없어진 뒤, 캐시가 메모리에서 완전히 제거되기까지 대기하는 시간.
- **Query Key**: 쿼리를 식별하는 배열(`["payments", userId]`). 캐시를 저장/조회/무효화하는 모든 기준점.

**동작 원리**
- staleTime이 지나면 데이터는 "stale(오래됨)"로 표시되지만, 캐시에서 즉시 사라지는 게 아님 — 화면엔 그대로 보여주면서(stale-while-revalidate) 백그라운드로 재요청해서 조용히 갱신함.
- gcTime이 지나야 실제로 메모리에서 삭제. 즉 staleTime은 "언제 다시 물어볼지", gcTime은 "언제 완전히 잊을지"를 결정하는 서로 다른 축.
- `queryClient.invalidateQueries({ queryKey: [...] })`로 특정 키의 캐시를 강제로 stale 처리해 즉시 재요청을 트리거할 수 있음 (결제 성공 후 결제 내역 쿼리 무효화 같은 패턴).

**내 프로젝트와의 연결**: 결제 시작/내역 이벤트를 추적하는 로직과 결합해, 결제 완료 시 관련 쿼리를 invalidate 하는 흐름을 그림으로 설명할 수 있으면 좋음.

## 8. FSD(Feature-Sliced Design)와 의존성 역전

**정의**: 레이어(app → pages → widgets → features → entities → shared)에 **위계질서**를 두고, 상위 레이어만 하위 레이어를 import할 수 있게 강제하는 아키텍처 방법론.

**동작 원리 / 이론적 배경**
- 이건 사실 전통적인 계층형 아키텍처(Layered Architecture)와 "의존성 역전 원칙(DIP)"의 프론트엔드 버전. 핵심은 **의존성 방향을 한 방향으로만 흐르게 강제**해서 순환 의존을 원천 차단하는 것.
- 각 슬라이스(feature, entity)는 `index.ts`를 통해서만 외부에 자신을 노출(Public API 패턴) — 캡슐화. 내부 파일 구조를 바꿔도 index.ts의 export만 유지하면 외부에는 영향이 없음(결합도를 낮추는 핵심 메커니즘).
- entities는 "명사"(User, Payment 같은 도메인 모델), features는 "동사"(로그인하다, 결제하다 같은 사용자 시나리오)로 구분하는 게 관습.

**내 프로젝트와의 연결**: 이 원칙을 사람이 리뷰로 지키게 하는 대신, `steiger`(정적 분석 도구)로 "레이어 규칙 위반 = import 그래프에서 허용되지 않는 방향의 의존성"을 코드로 탐지해 CI에서 자동 차단.

**흔한 오해**: "레이어가 많으면 무조건 좋은가?" → 아니오. 작은 프로젝트에선 오히려 탐색 비용만 늘어남. 팀 규모, 코드베이스 수명, 동시 작업 인원이 늘어날수록 이득이 커지는 트레이드오프.

## 9. 렌더링 전략 비교: CSR vs SSR vs SSG(Prerender) vs ISR

| 전략 | 렌더 시점 | 장점 | 단점 |
| --- | --- | --- | --- |
| **CSR** (Client-Side Rendering) | 브라우저에서 JS 실행 후 | 서버 부담 없음, SPA 전환 빠름 | 초기 HTML이 비어있어 SEO 불리, 첫 콘텐츠 노출 느림 |
| **SSR** (Server-Side Rendering) | 매 요청마다 서버에서 | 항상 최신 데이터, SEO 좋음 | 요청마다 서버 렌더링 비용, 인프라 필요 |
| **SSG/Prerender** (Static Site Generation) | 빌드 타임에 미리 | 서버 비용 없음(정적 파일), 매우 빠름 | 콘텐츠가 자주 바뀌면 재빌드 필요 |
| **ISR** (Incremental Static Regeneration) | 빌드 타임 + 주기적 재생성 | SSG의 속도 + 어느 정도의 최신성 | 구성 복잡도 증가 |

**하이드레이션(Hydration)이란**: SSR/SSG로 만든 정적 HTML은 "그림"일 뿐, 클릭 등 상호작용이 안 됨. 브라우저에 도착한 뒤 React가 이 HTML 위에 이벤트 리스너를 "부착"해서 살아있는 앱으로 만드는 과정.

**내 프로젝트와의 연결 (MetaDX 홈페이지)**: 콘텐츠가 자주 안 바뀌는 기업 홈페이지에 SSR(서버 필요, 매 요청 렌더링 비용)은 과하다고 판단 → 빌드 타임 prerender로 정적 HTML을 만들어 S3에 올리는 방식 선택. 검색엔진 크롤러는 이 정적 HTML을 그대로 읽을 수 있어 SEO 문제 해결.

## 10. Core Web Vitals: LCP / CLS / INP 정확한 정의

- **LCP (Largest Contentful Paint)**: 뷰포트 안에서 가장 큰 콘텐츠 요소(보통 이미지나 큰 텍스트 블록)가 렌더링 완료되는 시점. 2.5초 이내가 "Good".
- **CLS (Cumulative Layout Shift)**: 페이지 로드 중 예기치 않게 요소들이 밀리는 정도를 누적 점수화. 이미지/광고/폰트에 `width`/`height`(또는 `aspect-ratio`)를 미리 지정하지 않으면 로드되면서 레이아웃이 밀림. 0.1 이하가 "Good".
- **INP (Interaction to Next Paint)**: 사용자 상호작용(클릭 등) 후 다음 화면이 그려지기까지의 지연. 구 FID(First Input Delay)를 대체 — FID는 "첫 입력"만 쟀지만 INP는 페이지 생애주기 전체의 상호작용을 측정. 200ms 이하가 "Good".

**내 프로젝트와의 연결**: `fetchPriority="high"`는 LCP 요소(대표 이미지)를 브라우저가 더 일찍 요청하도록 우선순위 힌트를 주는 것 — LCP 개선과 직결. 스크롤 리렌더 제거는 INP/렌더 비용 감소와 연결지어 설명 가능.

## 11. 브라우저 리소스 로딩 우선순위: fetchPriority, lazy loading

**정의**
- `<img fetchpriority="high">`: 브라우저의 기본 리소스 우선순위 큐를 우회해, 이 리소스를 다른 이미지보다 먼저 다운로드하도록 힌트를 줌.
- `<img loading="lazy">`: 뷰포트에 가까워지기 전까지 이미지 다운로드 자체를 미룸(네트워크 요청 안 함).

**동작 원리**: 브라우저는 페이지 파싱하면서 발견하는 리소스(이미지, 스크립트, 폰트 등)에 내부적으로 우선순위를 매겨 다운로드 큐를 관리함. 기본적으로 뷰포트 밖 이미지는 낮은 우선순위지만, 개발자가 명시적으로 우선순위를 조정할 수 있게 해주는 게 이 두 속성.

**내 프로젝트와의 연결**: 대표 이미지(LCP 후보)는 `fetchPriority="high"`로 먼저 받고, 스크롤해야 보이는 나머지 이미지는 `lazy loading`으로 초기 로딩 경쟁에서 제외 — 초기 네트워크 대역폭을 LCP 요소에 집중시키는 전략.

## 12. JWT 인증에서 401 인터셉터와 토큰 갱신 레이스 컨디션

**정의**: API 클라이언트(axios 등)에 응답 인터셉터를 달아, 401(인증 만료) 응답을 가로채 자동으로 토큰을 갱신하고 원래 요청을 재시도하는 패턴.

**동작 원리 (기본 흐름)**
1. 요청 → 서버가 401 반환(access token 만료)
2. 인터셉터가 401을 감지 → refresh token으로 새 access token 요청
3. 새 토큰 저장 → 원래 실패했던 요청을 새 토큰으로 재시도

**레이스 컨디션 문제**: 화면에서 API 요청이 여러 개 동시에 나갔는데 access token이 만료된 상태라면, 여러 요청이 동시에 401을 받고 **각자 refresh를 호출**하게 됨 → refresh token이 여러 번 소모되거나 서버에서 거부당함.

**해결 패턴**: 첫 번째 401만 실제로 refresh를 실행하고, 그동안 들어온 다른 401 요청들은 "refresh가 끝날 때까지 대기하는 큐"에 넣었다가, refresh 완료 후 큐에 있던 요청들을 한 번에 재시도(Promise를 공유하는 락 패턴).

```ts
let refreshPromise: Promise<string> | null = null;

async function handle401() {
  if (!refreshPromise) {
    refreshPromise = refreshAccessToken().finally(() => { refreshPromise = null; });
  }
  return refreshPromise; // 동시에 들어온 요청들이 같은 Promise를 공유
}
```

**내 프로젝트와의 연결 (MetaDx Office)**: "401 인터셉터, 인증 가드"를 단위 테스트로 검증했다고 했으니, 이 레이스 컨디션 처리 여부를 실제로 확인하고, 처리했다면 위 패턴으로 설명하고 안 했다면 개선점으로 솔직히 답변 준비.
